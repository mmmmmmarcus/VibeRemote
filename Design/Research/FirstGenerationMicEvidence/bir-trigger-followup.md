# B439 BIR event 1 的来源复查（2026-10-13，仅静态）

## 范围与结果

本次重新从 [Apple OTA 来源](firmware-provenance.json) 获取并校验了
`B439-remote-v0118-hw000A-prod-signed.afu`，SHA-256
`9a2c3c002015ef5b11769c6c167a16a03829e5347ab971a4ee501f163022bbbc`。
使用仓库校验脚本封装分析 ELF，以完整 AFU 文件偏移 0 对应 `08008000`。
没有访问任何遥控器 API、发送按键或命令、运行诊断脚本、退出应用或修改设置。
这份证据只适用于历史 PID 026D / hardware 0A00 / v0118；**不适用于本轮另一只
PID 0314 / hardware 0021 / v0060 设备**，也不报告它的 LOCK。

**新增的有界结论：固件的四项已识别长按组合分支均未产生 BIR event 1。
内部 event 1 的生产者仍未找到，不能从已有接收端推出可用的解锁手势。**
未尝试任何物理组合。

## 四项组合的完整调度与分支

`HandleNewButtonEvent @0802FA10` 的 `0802FA70..0802FADE` 读取
`08066E84` 的四项 `(raw button mask, milliseconds)` 表。循环上限明确为 4；
每项与对象 `+2F0` 当前合成按钮状态做完整相等比较，而不是只测试其中一位。
匹配时将时长乘 1000，安排 callback `080302F8`，timer ID 为 `0B`。
callback 经全局 BIR 对象 `+100` signal 投递进入事件处理。

`HandleHeldButtonState` 的 `0802F1A8..0802F1DE` 比较同样四个原始值；
具体原始表存于 [bir-held-followup.json](bir-held-followup.json)，这里不将掩码翻译
成让用户尝试的按键操作。四条已识别路径如下：

| 固件诊断字符串 | 长按分支入口 | 最终操作（静态） |
|---|---|---|
| ADV | `0802F1C2` | `0802F492..0802F4B4` 发 BIR notification **3**，空 payload |
| ShutDown | `0802F2B8` | `0802F4AA..0802F4B4` 发 BIR notification **0**，空 payload |
| ATV Reset | `0802F29C` | `0802F47A..0802F480`，另一入口 `08031F90`，参数 `0B` |
| ATV DFU | `0802F2D4` | `0802F4CA..0802F4D6`，同一入口 `08031F90`，参数 `0C` |

不匹配分支 `0802F2F0` 只记录 `UNKNOWN`，回到共同结束路径。
上述 Reset/DFU 是固件日志名称，不是本次执行过的操作，也不能据名称认为它们
在重置本机 LOCK。另一入口的完整红外行为不在本次结论范围内；关键区别是它
没有在这些分支调用通知发射器来发送 event 1。

参考 [反汇编摘录](disassembly/bir-held-followup.txt)；JSON 同时保留字符串地址、
literal 地址及表的原始字段，便于独立复核。

## 通知发射器交叉检查

对完整 Thumb 线性反汇编搜索 `08059B88`（通用 notification emitter）的直接
`bl` / `b.w` 引用，得到 28 个候选调用点。既有 BIR 区域中仍只有：

- `0802F4B4`：上面的 event 0 或 3。
- `0802FB28`：event 2。
- `0802FB9C`：event 4，Siri 状态变化 payload。

对 AFU 在半字对齐处搜寻 `08059B88` / Thumb 指针 `08059B89` 的原始四字节值
未命中，因此没有发现以裸函数指针表调用该发射器的简单证据。
这是**有界的静态排除**：线性反汇编可能把数据当指令，可能漏掉跳转进入不同
对齐解码的代码；函数也可通过计算目标、间接包装或其他消息机制调用。
不能将此结果扩大成“固件里绝不存在 event 1 生产者”。

此前确认的下游链路保持成立：

`REMOTE NotificationProcess(source C80F, event 1)` → `080226A0` 发 REMOTE event 5
→ PMM event 5 分支 `08024CF0` → 持久写零函数 `08023160`。

目前缺口在**进入这条链之前**，不是解锁函数是否真的写存储。
可保留生产路径被条件编译移除、其他变体使用、或尚未解析的消息来源等假设；
没有证据足以在这些假设间下结论。

## 门禁与恢复限制复核

依据已保存的 [存储与恢复分析](unlock-storage-risk.md)，当前证据支持：

- `08023160` 直接向 factory store entry 0 写一个零字节，commit=1；没有在该
  函数里检查写结果或回读，也不即时更新 runtime LOCK。日志出现不是成功证据。
- 按键模拟 `31` 的普通入口仍受 runtime LOCK 限制；发现内部通知接收端不等于
  主机可以注入该内部事件，也不是绕过门禁的可执行命令。
- 静态 `ds set` 重锁路径要求运行时已解锁，能写回 1，但需要主机实际可访问
  CLI、完整写结果、重启及 E1 回读才能成为恢复流程。CLI 可达性由并行调查独立核对。
- 普通重启读取现存值；已识别 FactoryReset 操作 user store，不能自动重锁。
- 提交范围是含身份/校准的整个 factory bank。双副本与 checksum 不等于已有
  完整备份、可靠写入或失败后的可访问恢复渠道。
